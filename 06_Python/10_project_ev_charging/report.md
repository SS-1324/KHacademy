## STEP 5 · IQR 대신 도메인 규칙을 쓴 이유

이 데이터는 완속(7~11kW)과 급속(50~200kW) 충전기가 함께 섞여 있다. 전체를 하나의 분포로 놓고 IQR을 적용하면:

- 급속 충전소의 정상적인 대용량 충전이 "전체 기준"에서는 이상치처럼 보이고,
- 반대로 완속 충전소에서 100배 가까이 부풀려진 값이 급속의 정상 범위 안에 들어와 버려서 **못 잡는다.**

실제로 전체 `energy_kwh`에 IQR을 그대로 적용하면 215건이 잡히는데, 그중 도메인 규칙(③ 물리 상한 초과)과 겹치는 것은 94건뿐이고 나머지 121건은 IQR만의 오탐(비싼 급속 충전이 통계적으로만 튀어 보이는 것)이었다. 반대로 도메인 규칙 151건 중 57건은 IQR로는 아예 잡히지 않는, 완속 충전소에서 발생한 조작값이었다.

그래서 통계 대신 **"충전기 용량(kW) × 충전시간(h) × 1.1(측정오차 여유)"**이라는 물리적 상한을 직접 계산해서 각 행이 자신이 속한 충전기 종류·시간 기준으로 타당한지 판정했다. 여기에 "종료 시각 < 시작 시각"(물리적으로 불가능), "요금 음수"(논리적으로 불가능) 규칙을 더해 총 198건(중복 제외)을 제거했다.

## STEP 6 · 요금은 복원하고 충전량은 버린 이유

두 컬럼 모두 결측이었지만 처리 방식을 다르게 한 기준은 **"다른 컬럼으로부터 계산해 낼 근거가 있는가"** 다.

- `fee` (요금) : `energy_kwh × unit_price`로 정확히 재계산할 수 있다. 실제로 447건을 이 방식으로 복원했다.
- `energy_kwh` (충전량) : 이걸 역산할 수 있는 다른 컬럼이 없다. 평균이나 중앙값으로 채우는 것은 근거 없는 추정치를 실제 계량값인 것처럼 꾸미는 것과 같으므로, 대신 313건을 제외했다.

(참고로 `energy_kwh` 제거 후, 결측이었던 `fee` 13건 — energy_kwh도 함께 결측이라 애초에 복원이 불가능했던 행들 — 도 자연스럽게 함께 제거되어 최종 결측은 0건이 되었다.)

## 알아둘 것 하나 (구현 중 발견한 함정)

STEP 5에서 `capacity_kw`를 nullable `Int64` 타입으로 만들어 뒀는데, 이 타입과 `energy_kwh`의 NaN이 섞여 비교 연산을 하면 결과가 `False`가 아니라 `pd.NA`가 된다. `rule1 | rule2 | rule3`에서 이 NA가 Kleene 논리로 전파되고, `df[~mask]`로 인덱싱할 때 NA인 행까지 함께 빠져버려서(198건이 아니라 511건이 빠짐) 최종 행 수가 크게 어긋났었다. 각 규칙에 `.fillna(False)`를 명시해서 해결했다 — nullable 타입과 결측이 섞인 boolean 연산은 항상 이 점을 조심해야 한다.

## 심화 1~3 · ETL 분리 / 로깅 / 검증 함수

`pipeline/` 패키지로 분리했다.

```
pipeline/
  config.py     경로·상수, _db.py/_config.py 재사용
  logger.py     화면 + 파일(logs/YYYYMMDD.log) 동시 기록
  extract.py    CSV 3장을 있는 그대로 로드
  transform.py  STEP2~6 함수 + validate()
  load.py       UPSERT 적재 + verify()
  pipeline.py   Extract -> Transform -> Validate -> Load -> Verify 조립
```

`10_run_pipeline.py`로 테이블을 비운 뒤 두 번 연속 실행해 확인:

| | 1회차 | 2회차 |
| --- | ---: | ---: |
| 신규 | 11,459 | 0 |
| 갱신 | 0 | 0 |
| 최종 행 수 | 11,459 | 11,459 |

`validate()`는 STEP1~7의 스크립트에서 눈으로 확인했던 8가지 조건(날짜 타입, `log_id` 중복 0, 결측 0, 시간·요금 논리, 표기 통일)을 자동으로 재확인하고, 하나라도 실패하면 `Load` 단계로 넘어가지 않고 파이프라인을 중단한다.
